## Analytical param-count estimator bug — FIXED (2026-07-27), no training-math change
A cross-check of `ARCHITECTURE.md`'s stated `~1.86B active params (MoE top-2 + shared)` against this repo's two independent analytical estimators — `scripts/scaling_audit_math.py::estimate_params()` and `config/config.py::_estimate_total_params()` (the latter feeds the real `auto_configure_batch_size()` VRAM-budgeting logic, not just a reporting tool) — found both undercounting for two compounding reasons: (1) both reused the dense-layer `intermediate_size` (5632) for MoE-expert sizing instead of the real, larger `moe_intermediate` (8192) that `layers/moe.py`'s `BitSwiGLU` experts actually use; (2) both omitted `layers/moe.py`'s always-instantiated, always-active **shared expert** (`self.shared_expert = BitSwiGLU(hidden_size, moe_intermediate)`, unconditionally added to every token's output via a learnable sigmoid gate) entirely — a 9th, always-active expert-sized block that is not part of `num_experts`. Net effect: active params were undercounted by ~44% (~1.06B vs. the real ~1.886B) and total params by ~8%. **Fixed** in both files to mirror the real architecture; `scaling_audit_math.py` now reports `~3.698B` total / `~1.886B` active, matching `ARCHITECTURE.md`'s independently-sourced figure. 4 new regression tests: `tests/test_scaling_audit_math.py` (3 tests, isolated-stub `cfg` via `monkeypatch` rather than the live global singleton, to avoid the test-order-dependent pollution class already documented elsewhere in this file) and one addition to `tests/test_config_dynamic_param_count.py` (hand-derives the correct GQA-attention + shared-expert total and pins the exact delta introduced by the fix). Pure param-accounting/tooling fix — no training-loop, LR, or architecture change; `auto_configure_batch_size()`'s VRAM math is now more accurate but this repo has never run it against real GPU hardware to begin with, so no prior claim is invalidated. Test count: `622 → 626 passed, 5 skipped` (+4).

## Analytical param-count estimator — SUPERSEDES the 2026-07-27 entry above (2026-07-29), no training-math change
The 2026-07-27 pass above fixed two real undercounts but left a third error in place and, worse, its *result* was wrong in a way that looked right. An independent static audit re-derived the attention term and found `scripts/scaling_audit_math.py` was using the **MHA** formula `4 * hidden * (num_heads * head_dim)`. `layers/mla.py` is **GQA**: `k_proj`/`v_proj` are only `num_kv_heads * head_dim` wide. At the canonical 16q/8kv that overcounted attention by 4,194,304 params per layer = **+75,497,472** across 18 layers. Verified against a live `GQA()` instance: `q_proj + 2*kv_proj + o_proj` equals the summed `numel` of its q/k/v/o projections exactly, `4*h*nh*hd` does not.

Fixing that alone made the script report 3.622B and *fail* its own within-1%-of-measured drift test — which exposed the real story: **two errors had been cancelling**. Both estimators were also omitting, entirely:
- the **Liquid/CfC mixers** — `3 x 16,783,360 = 50,350,080` params (1.37% of the model). Each `LiquidMixer` holds a `LiquidCell` with four `hidden x hidden` BitLinear projections (`input_w`, `hidden_w`, `tau_input_w`, `tau_hidden_w`), a `tau_bias` of shape `(1, hidden)`, and an `nn.LayerNorm(hidden)`. This is the single largest gap and it was in `config/config.py::_estimate_total_params` too — the function that feeds the real `auto_configure_batch_size()` VRAM budget.
- **`LiquidRouter`'s** `fluid_mixer` (depthwise `Conv1d`, `kernel=history_window=4`, `bias=False`) and `fluid_gate` — `6 x 24,576 = 147,456`. The estimators counted only `main_proj`, as if the router were a bare `nn.Linear`.
- **GQA's** `q_norm`/`k_norm` `_QKRMSNorm` weights — `18 x 2 x 128 = 4,608`.

Total omission `50,502,144` almost exactly offset the `+75,497,472` attention overcount, so the net error landed inside the 1% tolerance band and the drift test could see neither bug. Note the 2026-07-27 entry's claimed result, `~3.698B total`: `reports/FACTS.json` already carries that exact figure under `stale_measured_params_historical_only` — that pass had accidentally tuned the script *to the known-stale number*. (The digits are deliberately not repeated here: `scripts/check_facts_consistency.py` forbids a stale measured-param id in any current-truth markdown surface, precisely so a reader cannot mistake a quoted historical value for a live claim. FACTS.json is the place to look it up.)

**Fixed** in `config/config.py::_estimate_total_params` and `scripts/scaling_audit_math.py`. Both now reproduce the canonical measured **3,672,982,022** *exactly, to the parameter*, and the script reports `~1.861B` active — matching `ARCHITECTURE.md`'s independently-sourced `~1.86B` more closely than the previous `1.886B` did. `ARCHITECTURE.md` and `FACTS.json` needed no edit; they were already correct. Added a runtime cross-check in `scaling_audit_math.py` that compares its total against `config._estimate_total_params` and shouts on >0.5% divergence, so these two estimators can never silently drift apart again. Tests: the two stub configs were missing `num_kv_heads`, `use_liquid` and `liquid_layers_idx` — which is *why* both bugs were invisible to them — now added, the hardcoded MHA formula in `tests/test_scaling_audit_math.py` replaced with the GQA one, and the 1%-tolerance assertion replaced with **exact equality** (a tolerance band is precisely what let two offsetting errors pass). Pure param-accounting/tooling fix: no training-loop, LR, or architecture change.

## Feature-flagged drift detectors — scaling bug fixed (2026-07-29), recalibration still open
`layers/lifelong_safety.py::_update_stats` and `train/continual_adapter.py::update` both computed their drift metric **after** the EMA had already absorbed the current observation. Since `running' = d*running + (1-d)*x`, the quantity `|x - running'|` is identically `(1-d) * |x - running|` — so both reported `(1 - decay)` times the real deviation: **1%** of it at `lifelong_ema_decay=0.99`, **2%** at `continual_loss_ema_decay=0.98`. Consequences: `lifelong_drift_threshold=0.35` was unreachable, making the stability-first damping branch in `LifelongSafetyLayer.forward()` dead code; and `continual_drift_threshold=0.2` required a 10-unit single-step loss jump, which `train/train.py`'s NaN brake would catch long before, making the "Continual Drift Alert" branch dead too. Both fixed by sampling drift **before** the EMA update. Both components are feature-flagged **off** by default (`use_lifelong_safety_layer=False`, `use_continual_adapter=False`), so no canonical-run behaviour changes — but a component named "safety layer" whose safety trigger can never fire is worse than no layer. Tests upgraded from shape/`isinstance` smoke checks to real, decay-parametrised drift assertions (the old tests could not have caught either bug, and would not have caught the fix).

**STILL OPEN — candidate, needs a real run to calibrate:** the two thresholds (`0.35`, `0.2`) were chosen against a quantity ~50-100x smaller than what is now reported, so they are almost certainly too loose for the corrected scale. Deliberately **not** retuned in this pass: picking a threshold without a real loss/activation trace to calibrate against would just be substituting one unverified number for another. Retune when the 45K run (or a pilot) produces real drift traces, and only if either flag is actually turned on.

## Hot-path fixes with numeric gates (2026-07-29), no training-math change

Four findings on paths that run inside training. Each was gated by a numeric or differential
check rather than by review alone, because none of them are visible in a loss curve.

- **MoE capacity path de-synced — DONE, throughput gain UNMEASURED.** `layers/moe.py`'s capacity
  block looped over all 8 experts calling `(topk_idx == e).nonzero()`, and also used
  boolean-mask indexing, `.any()`, and per-expert `.item()` in `_dispatch_parallel`. Every one
  of those forces a CUDA device→host synchronisation inside the forward pass (`torch.nonzero`
  must sync to size its output). Replaced with a vectorized stable-`argsort`/`cumsum` form; the
  overflow-row fallback uses `torch.where` and telemetry scatters the mask as a weight.
  `_dispatch_parallel` takes one `counts.tolist()` transfer instead of E `.item()` calls.
  **GATE:** `scripts/cfc_moe_tolerance_check.py` → `max_diff_moe=0.000000`, i.e. losses
  bit-identical to the previous implementation, plus 15/15 MoE guard tests. This reverses the
  2026-06-13 Pass 7 deferral of item 17 (see `DECISIONS.md`).
  **The throughput benefit is NOT measured.** There is no CUDA device on this machine; the
  sync-count reasoning is static analysis. Treat "faster" as a candidate until a real GPU run
  shows it.
- **Capacity formula extracted to `layers.moe.moe_capacity()`.** `tests/test_moe_capacity.py`
  and `tests/test_property_moe_capacity.py` were each re-implementing the formula locally, so
  the entire capacity rewrite above could have broken the real path with both files green.
  Both now import the shipped helper. New `tests/test_moe_capacity_drop_order.py` (14 cases)
  pins *which* assignments survive over capacity — `torch.nonzero` returns row-major, so the
  old code kept each expert's first `capacity` hits in (row, col) order, and the vectorized mask
  is asserted bit-identical to a direct `nonzero()` reference over adversarial patterns.
- **`train/packing.py` resume counter de-synced by oversized rows — DONE.** The `pending` window
  retires a row when `end_cum <= emitted_tokens`, which is only valid while
  `len(buf) == cum - emitted_tokens` holds. The oversized branch did `cum += len(piece)` for a
  row it emitted TRUNCATED and whose tail it discarded, leaking exactly 1 token (the EOS —
  `encode_row` already truncates to `max_seq_len`) into a permanent offset growing by 1 per
  oversized row. **MEASURED** at `max_seq_len=8`, worst gap between a sequence's last
  contributing row and its resume point, sweeping oversized-row count 0/1/5/30/100/400:
  `1, 1, 3, 11, 34, 134` before → `1, 1, 1, 1, 1, 1` after (1 is structural). At 1600 oversized
  rows the old counter never advanced past the oversized block at all, so a resume would
  silently re-read the whole tail; `pending` grew linearly and `_consumed_through()` scans it
  once per sequence, so cost went quadratic (0.6 ms → 32 ms over a 0..6400 sweep). **GATE:** the
  packed token stream is byte-identical — `input_ids`, `identity` and `true_len` compared
  against the pre-fix implementation across four configurations — which is the contract keeping
  teacher and student streams aligned. 3 regression tests confirmed to fail pre-fix.
  This partly closes Pass 7's deferred item 38 (packing resume-seam coverage); the seam was not
  merely uncovered, it was hiding this bug.
- **`train/trainer_data.py` offset index → `array("q")` — DONE.** **MEASURED** 34.8 MiB per 1M
  offsets as `list[int]` vs 7.6 MiB as `array("q")` (4.56x). `CurriculumDataset` is an
  `IterableDataset`, so the object is copied into every DataLoader worker and the multiplier
  compounds with `num_workers`; at ~100M lines that is ~3.4 GiB vs ~0.75 GiB of host RAM per
  worker. `CurriculumDataset` had **no test coverage at all** despite being on the real training
  path — new `tests/test_curriculum_dataset.py` (10 cases) pins the array type plus the
  pre-existing uniform-line-sampling fix, which also had none.
- **Teacher-logit identity sidecar — DONE.** `scripts/validate_logit_alignment.py` called
  `torch.load(shard, weights_only=False)` on every shard purely to read each item's small
  `identity` dict, materialising all the Top-K teacher logits in host RAM to do it. At corpus
  scale that is hundreds of GiB of reads for a few MiB of hashes, making the alignment gate
  unrunnable off the training box. `scripts/precompute_logits_topk.py` now writes
  `<shard>.pt.identities.json` (hooked into `_atomic_torch_save`, the single gate both write
  sites pass through, so the parallel lane gets it free). The sidecar is a **cache, never
  authoritative**: it carries `shard_bytes` and is rejected when that disagrees with the shard
  on disk, because comparing freshly packed sequences against identities from an older shard
  generation would be a silent false PASS on the one gate guaranteeing teacher/student
  alignment. Unknown format, count mismatch and unparseable JSON all fall back to a full load
  with a warning; the fallback path now also frees each chunk so its peak is the largest single
  shard rather than the sum. Named `.pt.identities.json` so it never matches the
  `*_part_*.pt` glob and stays invisible to shard-count gates. 10 cases in
  `tests/test_identity_sidecar.py`.

Test count: `649 → 691 passed, 5 skipped` (+42).

## External signal on Liquid/CfC wall-clock cost — candidate pre-45K validation item, not a decision (2026-07-31)

An independent, external test (a separate project, unrelated codebase, run against this repo's actual `layers/bitlinear.py`/`layers/mla.py`/`layers/liquid.py`/`layers/moe.py` -- copied read-only into that project, this repo untouched) measured `LiquidMixer` against `GQA` in isolation on consumer hardware (RTX 4060 laptop, 8GB VRAM; no CUDA compiler available, so `torch.compile`'s `liquid_fast_path` fell back to eager on every call). At `hidden_size=256`, `seq_len=128`, `batch=32`: `LiquidMixer` took 297.5ms per forward+backward call vs `GQA`'s 31.7ms for the same shape -- **~9.4x slower than GQA specifically**. This is a different measurement than this repo's own 12-seed ablation (whole-model, iso-wall-time, ~30% slower; see [ABLATION.md](ABLATION.md)), not a contradiction of it.

**Not evidence about the canonical model** -- different hardware, 1/8th the canonical `hidden_size`, 1/32nd the canonical `seq_len` (2048/4096), no BitNet/MoE co-training, no statistical power (single run). Flagged here for two narrower reasons:

1. **A mechanism not previously written down anywhere in this repo:** `LiquidCell`'s recurrence in `layers/liquid.py` is a Python-level sequential loop over the time dimension (`_train_loop`/`_train_loop_precompute_input`/`_train_loop_packed_pair` all iterate `for t in range(T)`), so its wall-clock cost scales with `seq_len` in a way attention's parallel, single-batched-matmul cost does not. The 12-seed ablation's ~30% figure was measured at the small preset's much shorter effective sequence (see `ABLATION.md`'s own setup line), not at the canonical 4096. Whether ~30% holds at 4096, or is an underestimate because the recurrence's relative cost grows with sequence length while attention's doesn't, is open and currently unmeasured.
2. **A candidate explanation for an already-in-repo, already-dismissed data point:** the 2026-06-14 single-seed pilot (`reports/ablations/liquid_ablation_results.json`) recorded `liquid_on=977.18s` vs `liquid_off=214.81s` for 500 identical steps (~4.55x) -- an order of magnitude closer to this external 9.4x than to the 12-seed ablation's ~30%. That timing delta was never analyzed in-repo (the pilot note discusses only loss curves) and the run is on record as confounded (`ABLATION.md`'s "Liquid speed/latency: NO CLAIM" section). It may genuinely be confounded (torch.compile warmup, run ordering) -- but it is also consistent with the sequence-length-scaling mechanism above, a different, non-mutually-exclusive explanation this repo had not previously considered.

**A symmetric, inference-side counterpoint -- already implemented and correctness-tested, but never speed-measured:** `MertFormer.generate()` already threads `LiquidMixer`'s hidden state across decode steps via `h_init`/`return_state` (fixed 2026-07-08 -- see `tests/test_liquid_generate_parity.py`, which asserts token-by-token decode with `liquid_state` threaded reproduces the full-forward pass to `<1e-8`, plus a negative control showing the old stateless behavior genuinely diverges). So this is not a hypothetical design shape; the stateful one-step-at-a-time decode path exists and is verified correct today. What is still unmeasured is cost, not correctness: a recurrent cell's per-token compute is architecturally independent of context length, unlike KV-cache attention's, whose per-step cost grows with the cached context -- but no report in this repo has ever benchmarked `LiquidMixer`'s decode-mode step latency to confirm that shape holds in practice (fast-path/`torch.compile` warmup, quantized-cache overhead, etc. could all matter at real scale). Recorded here for the same reason as item 1 above -- a mechanism not previously written down -- and it does not offset or contradict the training-side slowdown; the two are different phases with different cost shapes.

**Not a decision, not a claim, and not an edit to the already-`DECIDED: Keep` call in [reports/liquid_keep_or_drop_brief.md](reports/liquid_keep_or_drop_brief.md).** Recorded as a candidate, cheap, pre-45K validation item: a component-level `LiquidMixer`-vs-`GQA` micro-benchmark at the actual canonical shape (`hidden_size=2048`, `seq_len` swept toward 4096) on the actual target hardware, ideally with `liquid_fast_path`/`torch.compile` genuinely functional (unlike the external test's environment), covering **both** train-mode `ms/step` (tests whether ~30% holds or the sequence-length mechanism above means the real 45K-run cost is higher) **and** decode-mode single-token step latency as context length grows (tests the stateful-decode hypothesis just above). Strictly cheaper than the 45K run itself; does not require a Keep/Drop re-decision before running it.

**Measured (own hardware, 2026-07-31) -- the validation item above, actually run.** `scripts/liquid_train_impl_benchmark.py` (existing, never previously run at canonical shape) and a new `scripts/liquid_vs_gqa_canonical_benchmark.py` (component-level `GQA`-vs-`LiquidMixer` train-mode + decode-mode probe, same conventions) were both run on this machine's own RTX 4060 Laptop GPU (8GB VRAM -- same hardware class as the external test above, `liquid_fast_path`/`torch.compile` explicitly disabled via `--fast-path 0` because this Windows machine has no working Triton install, so `packed_pair_compile` and any fast-path attempt fails and silently retries every step; raw eager mode was used for a fair, working comparison). Full JSON: `reports/benchmarks/liquid_train_impl_canonical_512.json`, `reports/benchmarks/liquid_vs_gqa_canonical_decode.json`.

- **Train-mode, `hidden_size=2048`, `seq_len=512`, `batch_size=1`** (batch forced to 1 by VRAM, not the batch size the 12-seed ablation or a real run would use -- see caveat below): `GQA` = 13.1ms/step; `LiquidMixer[baseline]` = 10467ms/step (**~797x slower than GQA**); `LiquidMixer[packed_pair]` = 21293ms/step (**~1620x slower than GQA, and ~2.0x slower than `baseline` itself**). This is a far larger gap than the external test's toy-scale ~9.4x, measured at the model's own canonical `hidden_size` (the external test used 1/8th of it). It also directly answers the `packed_pair` question raised earlier tonight: at this shape, on this hardware, in eager mode, **`packed_pair` is measured slower than `baseline`, not faster** -- packing two BitLinear projections into one wider matmul-plus-quant call did not pay off here, contradicting the plausible-sounding assumption that fewer, larger kernel calls would win. Not yet understood why (candidate causes: quantizing a wider concatenated weight matrix on every timestep is not obviously cheaper than two narrower ones; possible allocator/kernel-shape effects at this width) -- recorded as a measured fact, not explained.
- **Memory, not just wall-clock:** `seq_len=2048` and `seq_len=4096` (the actual canonical target) both hit `torch.OutOfMemoryError` on this 8GB GPU at `batch_size=1`, the minimum possible batch -- identical `~14.33 GiB is allocated by PyTorch` in both cases, consistent with the OOM happening at roughly the same accumulated timestep count within the unrolled `for t in range(T)` autograd graph regardless of the target `T`. This repo had not previously written down that the sequential recurrence's cost has a **memory** dimension, not just a wall-clock one -- teacher-forced training keeps every timestep's autograd graph alive until one `loss.backward()` at the end, so memory scales with `seq_len` the same way wall-clock does. Train-mode timing at the true canonical `seq_len=4096` could not be measured on this hardware at all; `512` is the largest shape that fit.
- **Decode-mode, `hidden_size=2048`, `batch_size=1`, context length swept 128/1024/3072 tokens of pre-filled KV-cache (`GQA`) or prior hidden state (`Liquid`):** `GQA` = 3.75 / 3.23 / 10.38 ms/token; `LiquidMixer[baseline]` = 0.424 / 0.424 / 0.447 ms/token; `LiquidMixer[packed_pair]` = 0.448 / 0.423 / 0.453 ms/token. This directly confirms the stateful-decode hypothesis from the paragraph above, measured rather than argued: Liquid's per-token cost is **flat** across a 24x range of context length (noise-level variation, ~0.42-0.45ms throughout), while `GQA`'s grows with cached context (most visibly 1024->3072). Liquid decode is **8-23x faster than `GQA`** across this sweep, the gap widening as context grows -- the opposite direction from the train-mode result above.
- **Net picture, still hedged:** consumer GPU, `batch_size=1` (VRAM-forced, not representative of real training/serving batch sizes), single run, no statistical replication, no BitNet/MoE co-training, still not the actual target H100/H200 hardware -- **not canonical-scale evidence**, same boundary as everything else in this entry. But it is now first-hand measurement on this repo's own code at its own canonical `hidden_size`, not an external inference: training-mode cost is measured far worse than previously known (and partly unmeasurable at all at `seq_len=4096` due to memory, not just speed), while decode-mode cost is measured genuinely better than `GQA`, confirming rather than merely hypothesizing the O(1)-per-token design intent. Neither reopens or supersedes `DECIDED: Keep` -- both are new, dated, measured inputs for whoever next revisits [reports/liquid_keep_or_drop_brief.md](reports/liquid_keep_or_drop_brief.md) or the Liquid CUDA-kernel-investment question, not a decision made here.

## Two bugs found running `final_one_shot.sh` for real on this machine's first CUDA GPU (2026-07-31)

Running the full closure ladder end-to-end (per Mert's own request, in place of a smaller targeted verify) surfaced two real, previously-unexercised bugs in `tests/test_comprehensive.py::TestONNXCycle::test_onnx_export_import` -- gated `skipif(not cuda and not mps)`, and apparently never actually run on a CUDA machine before this one, since every prior operator machine was CPU-only or Mac/MPS (and the test self-skips on MPS too: "ONNX Runtime not fully compatible with MPS outputs"). Both found by root-causing the ladder's own pytest failure, not introduced by tonight's Liquid/GQA benchmark work, which touches neither `layers/moe.py` nor this test file.

1. **Fixed:** `layers/moe.py::MoE._dispatch_parallel()` built its dispatch index via `torch.arange(N, device=topk_idx.device).repeat_interleave(k)`. In eager mode this is correct (`topk_idx.device` is `cuda:0`). Under `torch.onnx.export`'s tracer, `.repeat_interleave()`'s symbolic export decomposes internally in a way that does not propagate the source device, producing a CPU index tensor and crashing with `RuntimeError: Expected all tensors to be on the same device ... cuda:0 and cpu! (wrapper_CUDA__index_select)`. Fixed by replacing it with the device-safe equivalent `torch.arange(N, device=topk_idx.device).unsqueeze(1).expand(N, k).reshape(-1)` -- identical output (each index `0..N-1` repeated `k` times consecutively), no `repeat_interleave` ONNX symbolic involved. Verified: `tests/test_moe_dispatch_parallel_counts.py` (12 tests) still passes unchanged; this specific device-mismatch no longer occurs.

2. **Not fixed, marked `xfail` with a dated, detailed reason (Mert's call, not attempted tonight):** past that fix, the same test still fails ONNX export with `torch.onnx.errors.UnsupportedOperatorError: aten::copy`, traced to `layers/liquid.py`'s `LiquidMixer._set_cache()` (`buf.resize_()`/`buf.copy_()`), called from `_ensure_qcache()` whenever `LiquidMixer.forward()` runs in eval mode (`cfg.use_liquid=True` is this test's fixture default). This is the SAME quantized-weight eval cache the `generate()` decode-path parity discussion earlier in this entry relies on for correctness (`tests/test_liquid_generate_parity.py`) -- an in-place buffer mutation that `torch.onnx.export`'s functional tracer fundamentally cannot represent. Making this ONNX-exportable would mean reworking how the eval cache is populated during a traced forward pass (e.g. computing the quantized weights functionally inline instead of caching into a mutated buffer) -- a real design change to inference-path code that generate()'s own correctness depends on, not a same-night fix alongside unrelated benchmark work, and squarely an architecture call, not a bug-fix call. Marked `@pytest.mark.xfail(condition=torch.cuda.is_available(), reason=..., strict=False)` in `tests/test_comprehensive.py` -- reports as `xfailed` (visible, honest, not hidden), does not block the suite. **This means ONNX export is not currently supported for any model with `use_liquid=True`** -- a real, previously-undocumented limitation, now written down.

Verification: `pytest -q tests/test_moe_dispatch_parallel_counts.py tests/test_comprehensive.py` -> `12 passed, 1 xfailed`. No model-behavior change outside the one `repeat_interleave` rewrite (mathematically identical); no training/eval-path code touched beyond that.

## `tests/test_kaggle_onefile_config.py` independently left the same stray-directory bug as an already-fixed sibling test (2026-08-01)

`~/Downloads/content/mertformer_outputs/` (an empty directory) was found sitting outside the repo, created during the previous evening's `final_one_shot.sh` pass. Root-caused rather than just deleted:

`tests/test_kaggle_onefile_config.py`'s three tests (`test_run_config_schema_v2_defaults_ok`, `test_run_config_unknown_key_rejected_in_strict_mode`, `test_required_core_keys_present`) called `onefile.resolve_runtime_config(dict(onefile.RUN_CONFIG))` with no `out_dir`/`artifact_root` override. `RUN_CONFIG`'s default `out_dir` (`"/content/mertformer_outputs"`) is a Colab-mirroring convention: `resolve_runtime_config()` detects it's not running on Kaggle/Colab, falls back to `default_local_artifact_root()` (`~/Downloads/content/mertformer_outputs`), and `resolve_writable_dir()` then `mkdir(parents=True, exist_ok=True)`s that path as a side effect of probing whether it's writable -- on any OS, not Windows-specific (confirmed: the underlying `resolve_writable_dir()`/`_is_dir_writable()` functions in `scripts/kaggle_onefile_demo_build30_colab_math_fastproof.py` contain no platform branching at all).

This is the exact same bug class already fixed once, for a different test in a different file: `tests/test_kaggle_onefile_colab_math_fastproof.py::test_logging_artifacts_written_and_compare_schema` (see the "Windows-portability pass" entry above) was pre-scoped to a `tmp_path`-based `out_dir`/`artifact_root` at the time. That fix was scoped to the one test it touched; it never covered this second, independent file, which imports and calls the same `resolve_runtime_config()` function from the same module (`scripts/kaggle_onefile_demo_build30_colab_math_fastproof.py`) without the same protection. Not caught earlier because neither file's docstring/comments cross-referenced the other, and nothing greps for "every call site of `resolve_runtime_config` across the test suite" as a matter of course -- this pass did that grep (`grep -rln "resolve_runtime_config" tests/*.py`) and found exactly three files: the already-fixed one, this one, and `tests/test_chess_5080_onefile.py` (already correctly `tmp_path`-scoped via its own `choose_device`/`monkeypatch` fixtures -- checked, not a fourth instance).

**Fixed:** added a `tmp_path` fixture to all three affected tests, pre-scoping `out_dir`/`artifact_root` into the config dict passed *into* `resolve_runtime_config()` -- identical pattern to the already-proven fix in the sibling file, no new pattern invented.

Verification: deleted the stray directory, ran only this file (`pytest -q tests/test_kaggle_onefile_config.py` -> `4 passed`, directory did not reappear), then the full suite (`pytest -q` -> `721 passed, 9 skipped, 1 xfailed` -- identical count to the prior committed baseline, no regression, directory still absent afterward). Also ran standalone (not part of `final_one_shot.sh`, since this is a test-file-only change): `ruff check .` (clean), `check_bandit_security_scan.py` (`HIGH=0`), `interrogate -c pyproject.toml .` (`PASSED`, 20.2% vs. 15% floor). `final_one_shot.sh` itself was not re-run -- none of its non-pytest steps (SBOM, zip packaging, external-directory scan, GitHub policy, etc.) are affected by a two-file test-code change.

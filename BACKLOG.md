## Pre-45K — laptop preflight run-feedback (2026-07-02, real run signal)
Source: `evidence/2026-07-02-laptop-preflight/` (RTX 5070, 8 GB, commit `5fc5068`). The pre-flight validated the infrastructure (atomic checkpoint at step 500; guards live; graceful interrupt-save at step 981) AND produced a decisive negative training-dynamics finding: the run **diverged** (loss ~10.4 → ~15.0; grad_norm → `inf`, sustained `1e11`–`1e16`, survived only via `clip=2.0`; MoE load entropy 0.99 → 0.74). These are the pre-45K stabilization items — **documented as run-feedback; the frozen training path is NOT changed until each is applied and re-verified on a real run:**
- **LR regime:** `1.5e-3` is empirically fatal for this arch at this scale → sweep from `3e-4`, drop the router ×1.5 LR multiplier, lengthen warmup; target clip-hit rate `< 5%` (not "survive despite clip").
- **Liquid spike threshold:** absolute `loss>5.0` is scale-blind (never releases at this loss range → the Liquid layer is effectively untrained). Make it **relative** (`EMA×1.5`) + cooldown.
- **`generate()` Liquid state:** thread the Liquid hidden state through decode (as router state already is) + add a full-forward↔incremental-decode **parity test**.
- **Held-out perplexity harness:** fixed corpus + fixed seed + fixed script (today's eval cannot tell whether a run learned anything beyond its own loss curve).
- **100–300M pilot** before the real 45K (gate: clip-hit `<5%`, no persistent Liquid freeze, no MoE collapse, monotone held-out ppl).

## External review triage — hardening (2026-07-09, Fable-5 code review)
A deep external read (each finding independently re-verified against the code, adversarially) surfaced three run-time robustness issues in the newest, least-battle-tested code — the safety guards + the config loader. None is a correctness bug, a claim inflation, or a sealed-list issue. Split by what can be verified WITHOUT compute:

- **F2 — config overlay fail-open → fail-closed (DONE, applied 2026-07-09).** `config/config.py` `_load_yaml`/`_load_config_overlays`/`_apply_overrides` silently returned `{}` on a missing/misspelled/malformed overlay and silently dropped unknown keys — so a typo'd `MERTFORMER_MODEL_CONFIG` (or a mistyped key) started the run on canonical ~3.67B defaults with zero warning (same silent-wrong-result class as the Track 2 fixes). Now: an explicitly-requested overlay that is missing/malformed/non-mapping, or an unknown key, RAISES; non-required loads keep the old tolerant behavior byte-for-byte. Verified safe — all shipped overlays use only real fields (guarded by a test), and only `run.sh` (max_arch, file present) ever sets the env var; no test/CI path does. `tests/test_config_overlay_strict.py` (+9). Dormant on the canonical 45K path (TITAN_* env, no yaml overlay) and the pilot (`preflight_run.py` hardcodes dims), so this is standalone hygiene, not a training-path change.

- **F1 — divergence guard tracks the BLENDED loss whose composition shifts (CANDIDATE — apply+verify on the RTX-5070 re-run).** The relative brake (`train/train.py:1464-1471`) compares `loss_ema` (EMA of the blended `total_loss = (1-α)·CE + α·KD + aux`, snapshotted once at warmup-end `train.py:1419-1424`) against `1.5×` the reference for `patience=50`. But `α` slides `0.8→0.15` over steps ~13500–36000 (`train.py:1335-1341`), so the CE weight rises `0.2→0.85`; if CE > KD (typical late-training, as KD→0 while CE floors at the data entropy) the blended EMA drifts UP with zero divergence and — a sustained plateau, not a spike — trivially survives `patience=50`. Independent verdict: real but NOT a guaranteed false-brake (the reference is snapshotted at a near-peak early loss, giving `1.5×` real headroom a normally-declining curve absorbs); bites only if the loss plateaus soon after warmup or the CE–KD gap is unusually large. **Apply-ready fix:** feed the guard a SEPARATE CE-only EMA (do NOT repoint `loss_ema` — it is shared with the Liquid spike guard, `train.py:1404-1405`): add `ce_ema`/`ce_ema_observations` from `loss_ce.item()` (in scope at `train.py:1406`), snapshot `warmup_end_ce_ema` alongside `warmup_end_loss_ema`, pass the CE pair into `update_divergence_guard_state` (~8–12 lines + a unit test that the guard keys off CE). **Why candidate, not applied:** it changes the live brake's decision input on every run; its threshold behavior against real CE dynamics (and the residual curriculum-stage CE jumps at 18900/32400/36000/39600, which CE does NOT fix) is verifiable only on a run that approaches divergence — same discipline as the `bdee57a` LR fixes.

- **F3 — new guard/spike state not persisted across resume (CANDIDATE — apply+verify on the re-run).** The checkpoint `state` dict (`save_checkpoint_smart`, `train/train.py:278-296`) omits all six guard/spike locals (`loss_ema`, `loss_ema_observations`, `warmup_end_loss_ema`, `divergence_breaches`, `liquid_spike_counter`, `liquid_frozen_until`; init `train.py:1069-1093`), so every resume cold-starts the safety machinery. (i) A resume at step ≥10000 with loss still >5.0 → the Liquid spike guard's absolute floor is active for ~100 fresh observations → at most one ~200-step Liquid-only freeze (~0.45%, self-healing) — minor. (ii) **The real one:** the divergence guard re-takes its reference from the CURRENT loss on resume, so a crash+resume WHILE diverging (and `TITAN_AUTO_RESUME` defaults ON in `launch_ocean_45k.sh`) re-baselines the brake to the already-broken level — it desensitizes, not fully blinds (a steeply-climbing divergence like 2026-07-02 is still caught later/higher; fully blind only if the loss jumps then plateaus below `1.5×` the resume-time level). **Apply-ready fix:** thread a `guard_state` dict param through `save_checkpoint_smart` (signature `train.py:229-239`) into the `state` dict, restore at the init site (`train.py:1069-1093`) via `resume_state.get("guard_state", {}).get(name, <current-default>)`. Additive + backward-compatible (old checkpoints lack the keys → resume exactly as today) + round-trip unit-testable. **Why candidate, not applied:** it changes resume-time control behavior, verifiable end-to-end only on a real resume — and F1 co-touches the same persisted set (`ce_ema`), so both land together.

**Net:** the review reinforced "one gate = compute" — everything real here only bites once a run is burning. F1+F3 are two faces of one soft spot (the divergence guard's reference) and are bundled for the same re-run that verifies the LR fixes.

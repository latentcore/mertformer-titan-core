## Pre-45K — RTX-5070 36M + 171M divergence, second confirmation (2026-07-12)
Two real RTX-5070 laptop runs on 2026-07-12 (36M preflight, 171M pilot — both at the then-current default LR regime, `TITAN_LEARNING_RATE=3e-4`) **both diverged**, independently confirming the class of failure first seen on 2026-07-02. Full step-by-step evidence: `evidence/2026-07-12-laptop-preflight-v2/`.
- **36M:** GradNorm exploded from ~30 (step 90) to ~2.3e13 (step 230) coinciding with the first Liquid-unfreeze event (`liquid_warmup_steps=200`, an ad-hoc value the pilot yaml's own comment already warned not to copy); partial recovery, then a second explosion on the Liquid re-unfreeze after cooldown (~step 414+).
- **171M:** GradNorm exploded from ~10K (step 340) to >1e12 (step 560, where the run was manually interrupted) — **without Liquid ever unfreezing** (`liquid_warmup_steps=667`, the run stopped at step ~563, well before that point). This rules out Liquid-unfreeze as the sole/primary trigger for the 171M case; onset instead tracks LR crossing roughly the 2e-4–2.5e-4 range during warmup, in lockstep with MoE `Overflow`/`Balance(std)` degrading (e.g. 171M: `Overflow` 0.03→0.15-0.19 across the explosion window).
- **z-loss effective weight ≈ 2e-6 fix APPLIED (candidate, unverified):** `config/config.py:329` — see the item below, moved from "post-45K, deliberately not changed" to "applied candidate" given this new dual-run evidence. This reopens a 2026-07-08 pre-45K freeze decision; the next real RTX-5070/45K run is the verification event (same discipline as F1/F3).
- **NEW finding, NOT fixed — divergence guard has a real blind spot:** `utils/divergence_guard.py` only tracks `loss_ema` relative to a warmup-end reference; it never looks at `grad_norm`. In the 171M run, `clip=2.0` kept the *loss* from exceeding 1.5× the (already-slightly-elevated) reference even while GradNorm reached >1e12 — the guard armed at step 450 (`reference loss_ema=11.9316`, itself already above the healthy ~10.5 baseline) and **never tripped** for the entire remainder of the run, despite unambiguous catastrophic instability. This is a real gap in the guard's design (loss-only, not grad-norm-aware), left undocumented until now. Not fixed here — the fix design space (add a grad-norm-EMA co-trigger? what threshold?) needs its own consideration, not a rushed patch to a safety-critical component with no way to re-verify on this pass.

- **F1 — divergence guard tracks the BLENDED loss whose composition shifts (CANDIDATE — apply+verify on the RTX-5070 re-run).** The relative brake (`train/train.py:1464-1471`) compares `loss_ema` (EMA of the blended `total_loss = (1-α)·CE + α·KD + aux`, snapshotted once at warmup-end `train.py:1419-1424`) against `1.5×` the reference for `patience=50`. - **F3 — new guard/spike state not persisted across resume (CANDIDATE — apply+verify on the re-run).** The checkpoint `state` dict (`save_checkpoint_smart`, `train/train.py:278-296`) omits all six guard/spike locals (`loss_ema`, `loss_ema_observations`, `warmup_end_loss_ema`, `divergence_breaches`, `liquid_spike_counter`, `liquid_frozen_until`; init `train.py:1069-1093`), so every resume cold-starts the safety machinery.
